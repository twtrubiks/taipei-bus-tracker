## Context

現行到站資料的呈現路徑：

```
TDX/eBus → FallbackService → handler.GetETA（填 status 字串）→ JSON
         → useEta / useFavoritesEta（15s 輪詢）→ StopList / HomePage（顯示 eta.status）
```

`status` 欄位的消費者只有 React 前端。CLI（`cmd/notify/monitor.go:78`）有自己的 `formatETA`，dev tool（`cmd/test-tdx/main.go:107`）是自行呼叫 `model.ETAStatus(e.ETA)`，兩者都不讀 `StopETA.Status`。因此把狀態文字下放前端不影響其他消費者。

三級狀態的區間取自成熟公車 App 的普遍作法（0–90 進站中、91–179 將到站、≥180 約 N 分），比目前的「0–180 全部進站中」更貼近實際體感。

## Goals / Non-Goals

**Goals:**
- 秒數是唯一真值，顯示文字由消費端依秒數推導
- 畫面每秒有變化，但 API 請求維持 15 秒一次
- 倒數不說謊：資料過期時凍結並明示
- Web 與 CLI 對同一筆秒數給出一致的狀態文字

**Non-Goals:**
- 不改輪詢間隔（維持 15 秒）
- 不改背景分頁暫停輪詢的行為（背景通知是 Web Push 的範疇，另案處理）
- 不改快取 TTL 與 fallback 策略
- 不引入前端狀態管理套件

## Decisions

### 1. 倒數用「推導」而非「遞減」

**選擇**: 儲存 `(eta, fetchedAt)`，顯示時計算 `displayEta = eta - elapsed`。每秒只 bump 一個 counter 觸發重繪，不去改動已存的 eta 值。

**替代方案**: 每秒 `setState` 把每個 stop 的 eta 減 1。

**理由**: 遞減會讓「API 回來的真值」被逐秒覆寫，資料來源變得可變且無法回溯；一旦某次 tick 沒跑到（分頁切換、JS 卡頓）誤差就永久累積。推導法的真值永遠是最後一次 API 回應，tick 漏跑只是畫面晚一秒更新，下一秒自動修正。

### 2. 負值不倒數

**選擇**: `eta < 0` 直接原樣回傳，不參與倒數。

**理由**: 負值是狀態碼（-1 未發車、-2 末班已駛離、-3 交管不停靠、-4 未營運），不是秒數。對狀態碼做減法會得到無意義的值。

### 3. 過期 60 秒凍結倒數

**選擇**: `elapsed` 上限為 60 秒（`STALE_AFTER_MS`）。超過後倒數停在該點，UI 同時顯示「資料延遲」提示。

**替代方案**: 無上限持續倒數 / 資料過期即清空畫面。

**理由**: 輪詢間隔是 15 秒，正常情況 elapsed 不會超過 15。連續失敗 60 秒後若仍持續倒數，畫面會出現憑空捏造的「進站中」——寧可顯示凍結的舊值並標示延遲，也不要騙使用者。清空畫面則過度反應：舊資料仍有參考價值。

### 4. 狀態文字前後端各持一份實作

**選擇**: 前端 `web/src/utils/etaStatus.ts`（TS）與後端 `internal/model/eta.go`（Go）各自實作同一張對照表，兩邊都有測試涵蓋相同邊界值（0、90、91、179、180、181 與四個負值）。

**替代方案**: 後端繼續回傳 status 字串，前端 tick 時自行覆蓋。

**理由**: 由後端回傳字串的話，倒數中的秒數與字串會不一致（例如秒數已倒到 80 但字串還是 15 秒前算的「約 2 分」）。Go 側的實作無法移除——CLI 監控與 dev tool 仍需要它——所以兩份實作是必然，重點是用相同的邊界測試把它們釘住。

### 5. `status` 欄位直接移除而非保留

**選擇**: 從 `model.StopETA` 與 API 回應中移除 `Status`。

**理由**: 唯一的消費者（React 前端）在同一份 change 內改為自算。保留一個沒人讀又可能與前端不一致的欄位，只會製造下一個 bug 的溫床。

## Risks / Trade-offs

- **每秒重繪的效能**：路線詳情頁最多約 60 站，每秒重繪整份列表。React 對這個量級無壓力，且 tick 在分頁不可見時停止。若日後站數暴增再考慮 `memo`。
- **前後端文字實作漂移**：靠兩側的邊界值測試防護；修改對照表時必須同時更新兩份測試。
- **API 破壞性變更**：`status` 欄位移除屬 breaking change。本專案前後端同版部署（單一 binary 內嵌前端），無獨立的第三方 API 消費者，影響可控。
